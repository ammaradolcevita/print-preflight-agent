# Evaluation

**42 labelled files · precision 1.00 · recall 0.94 · about 65 ms per file**
(full table: [RESULTS_TABLE.md](RESULTS_TABLE.md), regenerate with `python eval/make_fixtures.py && python eval/run_eval.py`)

## How the set is built

`eval/make_fixtures.py` generates every file, so the correct answer is known:

- 6 good files (business card, flyer A5, poster A3, JPG card);
- 5 tricky files that should pass:
  - white card without bleed;
  - vector-only design;
  - a "300 dpi" image that is 299.8 dpi after rounding;
  - names and Dutch words;
  - a roll-up banner at 110 dpi;
- 26 files with one known problem (bleed, dpi, colour, safe zone, size, pages, fonts, text);
- 3 files with two problems at once;
- 2 files the tool is **expected to miss today** (known limits, kept in the set on purpose).

A check counts as "flagging" a file when it reports a warning or an error.

## What the evaluation caught

The first run had **2 false alarms**:
- a card with only 1 mm of bleed (87 x 57 mm) was called "the wrong shape";
- the same happened with 2 mm of bleed.

The size check only accepted the exact trim size or trim + full bleed. A page with *some* bleed is the right size with too little bleed, so it is a bleed problem, not a size problem.

**Fix:** the size check now accepts a centred trim with any bleed and leaves the amount to the bleed check. A regression test was added.

| | Precision | Recall |
|---|---:|---:|
| First run | 0.94 | 0.94 |
| After fix | **1.00** | **0.94** |

Earlier, the unit tests had found a similar issue. A "300 dpi" export was measured as 299.8 dpi after pixel rounding, which gave a warning. There is now a 2% tolerance, noted in `specs/print_specs.yaml`.

## The 2 misses, and what would fix them

| File | Missed | Why | Fix |
|---|---|---|---|
| `limit_rgb_vector_background.pdf` | colour | The colour check looks at pictures only. A background drawn as an RGB vector shape is not inspected. | Read the colour operators in the page content stream (`rg` = RGB, `k` = CMYK). |
| `limit_typo_inside_image.png` | text | The text is pixels, not text, so there is nothing to spell-check. | OCR (e.g. Tesseract) or a vision model on the rendered page. |

## Real-world style set (v0.2)

**20 files · 20/20 sensible verdicts · 0 crashes** (full table: [realworld/RESULTS_TABLE.md](realworld/RESULTS_TABLE.md),
regenerate with `python eval/make_realworld.py && python eval/run_realworld.py`)

The synthetic set above tests one problem at a time on clean files. This set copies the *structure*
that real design tools write, because that is where a preflight tool breaks on a customer's first upload:
Canva-style exports with and without bleed, crop marks with and without a TrimBox, an Illustrator file
whose MediaBox does not start at 0,0, a page stored with `/Rotate 90`, a card drawn on an A4 Word page,
front + back, vector-only, a spot colour, password-protected and permission-restricted PDFs, a PNG
export, a phone photo of a printed card, square and 90 x 50 mm cards, a 10 MB photo and a renamed Word file.
Each file is also run through the automatic fix.

The first run gave **13/20**. What it found, and what changed:

| Problem | Effect before | Fix |
|---|---|---|
| Crop marks without a TrimBox, design stops at the cut line | **"Print-ready"** although there was no bleed | The bleed check now also looks at the rendered page: colour just inside the cut line but nothing in the bleed = missing bleed. |
| TrimBox says 3 mm bleed, background stops at the cut line | **"Print-ready"** | Same content check. |
| Illustrator file, MediaBox not at 0,0 | Cut line placed 20 mm off: false text and safe-zone errors | The TrimBox is moved to the visible page's origin before use. |
| Page stored with `/Rotate 90` | False bleed and dpi errors | TrimBox, text and picture positions are turned with the page. |
| Spot colour (e.g. PANTONE) | Silently "print-ready" | Warning: spot colours are converted to CMYK and may look different. |
| Phone photo of a printed card | A size verdict on a photo | Honest message: this is a camera photo, please upload the design file. |
| Roll-up banner auto-fix | Rendered at 300 dpi (~240 megapixels) | Fix renders at most 40 megapixels, never below the product's minimum dpi. |

The synthetic scores did not change (precision 1.00, recall 0.94). Every case is a regression test
(`tests/test_realworld.py`).

**Limits:** these files are still generated by us, modelled on how the tools write PDFs. They are not
exports from the real tools. Real Canva/Illustrator exports can be added to `eval/realworld/real/`
with a `labels.csv`, and the runner picks them up.

## Honest limits of this evaluation

- The files are synthetic and generated by the same author as the checks, so the scores are optimistic.
- The next step is to test on real customer files, especially rejected ones (with permission), and report the same table.
- The spell-check uses English and Dutch dictionaries and skips capitalised words (names). Typos in names or in other languages are not caught.
- The CMYK conversion in the auto-fix uses MuPDF's colour management. A production version would use the printer's own ICC profile (e.g. FOGRA39).
